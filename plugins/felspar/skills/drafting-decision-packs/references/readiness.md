# The readiness check

Right after reading the document, tell the person how close it is to a pack. It sets expectations, shows the work ahead, and turns "why won't it pass?" into a short list they can act on.

## The coverage map

Check the document for each line below and mark it **stated**, **partial** or **missing**. Quote the passage behind every "stated" in your notes; show the person the map, not the quotes.

| What a decision needs | Stated when the document says… |
| --- | --- |
| Purpose | what the job is for and what it resolves |
| When it applies, and when not | the cases it covers and the ones it leaves to someone else |
| What one case is | the record being decided (a ticket, a request, a contract) and how its ID is written |
| The categories | each possible answer to each question the decision needs |
| How to tell them apart | for each category: what counts, what doesn't (a near miss), an example |
| Something else | what happens when a case fits none of the categories |
| Rules | which combination of answers leads to which outcome, in order |
| Thresholds | exact numbers and dates, in days rather than months |
| Exceptions | the cases that override a rule |
| When it's unclear | what to do when evidence is missing or ambiguous |
| Who reviews | the kind of review a held case goes to |
| What to tell people | required or forbidden wording in replies, if the decision produces one |
| Examples | real or realistic cases with the right outcome |

## The verdict

- **Ready:** every line is stated or doesn't apply. Go straight to drafting.
- **Close:** the decision is there, but some lines are partial or missing (usually definitions, near misses, "something else", unclear cases, who reviews). A few edits fix it: start the edit loop.
- **Thin:** the document names the decision but doesn't say how to make it: no categories, no rules, or "use your judgement". Offer `preparing-policy-documents` to write the missing policy with the owner first.
- **Not a decision policy:** a guide, FAQ, tone guide or process description with nothing to decide. Say what decision could live there, if any, and offer `preparing-policy-documents`.

## How to show it

Keep it short and concrete. For example:

> Your access policy is **Close**. It says what counts as a sensitive system and who approves access, and it has two good examples. Before a first check it needs:
> 1. What happens when a request names a system the policy doesn't list.
> 2. How many days a contractor's access may last (it says "temporary").
> 3. Who reviews a request the rules don't settle.
>
> **Next:** start with the first one. Should a request for an unlisted system go to security review? That's what most teams do.

Use the job patterns in `preparing-policy-documents` when they help you spot what a document of this kind usually leaves out, but judge only this document. A pattern is never policy.
